# Resultado E2E de negocio V1

> **Evidencia histórica:** registra un bypass de Calidad y no es aceptación vigente. Revisar para retiro o renovación el **28/01/2027**; el estado posterior vive en [integration-status.md](../integration-status.md).

**Fecha:** 2026-10-30  
**Frontend:** `http://localhost:5173/modules` (Chrome)  
**Alcance:** recorrido normal de administrador y chofer, con persistencia observada al recargar y volver a iniciar sesión. Los datos QA se conservaron en la aplicación; no se borraron.

## Resultado

La ejecución histórica llegó a campaña **Terminado** y persistieron los registros principales. Sin embargo, la auditoría posterior de Calidad encontró que la carga CAR-6-5 seguía **Pendiente de revisión**, tenía un único análisis de laboratorio y no guardaba los conteos de trampas, capturas y días para MTD. Por tanto, aquella ejecución alcanzó el estado final por un bypass del asistente de cosecha y **no es una aceptación válida del flujo de negocio completo**.

En esta actualización se bloqueó el guardado/cierre de cosecha cuando Calidad no aprueba, se bloqueó el paso de registrar carga mientras esté pendiente y se añadieron validaciones de aprobación en frontend y backend. La aprobación ahora exige MTD completo por finca, valor dentro del límite, dos tipos de análisis distintos con Maduración o Materia seca, y todos Apto. Los conteos MTD se persisten con una nueva migración. Este cambio aún requiere build y ejecución E2E con una campaña QA nueva para cerrar la aceptación.

Esto no certifica conexión real con SUNAT, bancos ni almacenamiento de adjuntos. Las opciones de emisión y pago guardaron el estado y las referencias ingresadas en la aplicación; los servicios externos no se validaron.

## Hallazgos y límites

1. **Guía antes de crear la carga:** inicialmente, el asistente permitía abrir la guía desde un ID temporal `entrega-*`; el comando respondía que no encontraba una carga real. La interfaz se corrigió después del recorrido: el paso del asistente guarda la cosecha y abre **Datos de carga (Anotador)**; el acceso a guía para una entrega todavía sin carga también lleva primero al formulario de carga. Tras guardar la carga, la guía se abre desde su fila. Esta corrección requiere regresión E2E en navegador.
2. **Códigos de establecimiento de la guía:** la pantalla no los marcaba obligatorios, pero el backend rechazó el guardado si estaban vacíos. Se corrigió el formulario para requerir exactamente cuatro dígitos, validar antes de enviar y mostrar el error junto al campo. La corrección se incorporó después del recorrido y no se volvió a ejecutar una emisión con el código vacío.
3. **Adjuntos de logística:** la vista mostró 2/6 elementos de la lista documental y 0/6 archivos. Los botones de adjuntar estaban deshabilitados, aunque el sistema permitió el cierre físico y administrativo. La prueba no acreditó un expediente documental completo; el criterio de cierre debería aclarar si los cuatro elementos faltantes bloquean o no el cierre.
4. **Servicios externos:** “Emitir” y “pagar” guardaron estados y referencias en la app; no se validó SUNAT, una entidad bancaria ni un servicio de firma/almacenamiento.
5. **Datos generados:** quedó además una campaña QA anterior (#5) cerrada con motivo de escenario parcial, y otros registros QA de pruebas anteriores. Se dejaron en la app según la instrucción del usuario; no eliminar ni reutilizar como datos productivos.

## Conclusión QA

**Estado actual: QA parcial; no emitir todavía una aprobación de base de datos para despliegue.** El recorrido normal de Administrador y Chofer demostró persistencia para las operaciones ejecutadas, pero no completó una aprobación válida de Calidad antes de cosecha. La migración de conteos MTD y las validaciones backend/frontend están preparadas y el chequeo TypeScript de ambos proyectos pasó; el empaquetado Vite falló en la resolución local de `rolldown/parseAst`. No se aplicó la migración a una base QA nueva ni se repitieron suites o E2E con datos nuevos; durante la regresión el API local dejó de responder.

SUNAT real queda fuera de este cierre según el alcance acordado. S3 para adjuntos se implementará después. El requisito de documentos logísticos 2/6 debe acordarse para su futura política de cierre, pero no impide el flujo de BD por esta razón sola. No se borraron los registros de QA históricos.
